# Process narrative: how this Bicep adoption kit was produced

## 1. Validate the source artefacts

The first task was to establish whether the Cloud Shell capture had actually failed. Both uploaded ZIP files were tested before any design work:

- `sharecloud-current-infra.zip` contained 17 files;
- `sharecloud-iac-snapshot.zip` contained 11 JSON files;
- neither archive contained a zero-byte file;
- every snapshot JSON file parsed successfully;
- both ZIP integrity tests completed with no errors.

The apparent failure was therefore only a lack of visible success output during the original shell run. The required artefacts were created successfully.

## 2. Separate the two existing infrastructure concerns

The current repository archive was inspected first. It showed that the existing Bicep stack is primarily the **frontend/application-hosting stack**:

- subscription-scope resource-group orchestration;
- Container Registry;
- Container Apps Environment and Container App;
- user-assigned managed identity;
- backend and browser Application Insights;
- Entra application handling.

The live snapshot, by contrast, described the **backend/AI platform stack** in the `ShareCloud` resource group:

- VNet and subnet;
- Log Analytics and Application Insights;
- Storage, Cosmos DB and Key Vault;
- Azure AI Search;
- Foundry account, project and model deployment;
- Foundry project connections.

Rather than combine two working deployment models into one large template, the new stack was placed under `infra/backend`. This preserves the existing frontend deployment and creates a clear operational boundary.

## 3. Normalize live Azure responses into desired state

`az resource show` and REST responses contain many properties that should not be copied into IaC, including:

- resource IDs and etags;
- provisioning state and status;
- generated endpoints and timestamps;
- principal IDs generated by system-assigned identities;
- model `currentCapacity` mirrors;
- internal IDs and agent identity blueprints;
- service-managed metadata.

For each resource, the live response was reduced to **writable, intentional configuration**. For example:

- Cosmos DB retained serverless capability, Session consistency, continuous seven-day backup, network rules and TLS 1.2, but not generated endpoints or key metadata;
- Foundry retained AIServices/S0, project management, system identity, public access and its current network ACLs, but not associated-project/status fields;
- the project retained display name, description and system identity, but not the server-generated internal and agent-identity fields;
- the model deployment retained model name/version, SKU, capacity and upgrade policy, but not `currentCapacity`.

This is the key difference between a deliberate IaC conversion and blindly checking an ARM export into source control.

## 4. Map each resource to a deployable Bicep API version

The generated modules use stable resource-provider versions that support the captured properties:

| Resource | API version |
|---|---|
| Virtual network | `2025-03-01` |
| Log Analytics | `2023-09-01` |
| Application Insights | `2020-02-02` |
| Storage account | `2025-06-01` |
| Cosmos DB account | `2025-04-15` |
| Key Vault | `2024-11-01` |
| Azure AI Search | `2025-05-01` |
| Foundry account/project/model | `2025-06-01` |
| Foundry project connections | `2025-06-01` |

The choice was based on current Microsoft resource references and on the properties visible in the live snapshot. Newer preview APIs were avoided where a stable version was sufficient.

## 5. Reconstruct dependencies rather than copy resource order

Azure export order is not dependency order. The modules were arranged by actual dependency:

```text
VNet/subnet
   ├── Storage network rule
   ├── Cosmos network rule
   ├── Key Vault network rule
   └── Foundry network rule

Log Analytics
   └── Application Insights

Foundry account
   ├── Foundry project
   ├── model deployment
   └── Foundry principal ID
          └── legacy Key Vault access-policy preservation

All core services
   └── optional project connections
```

Bicep module outputs are used for resource IDs and endpoints instead of hardcoding subscription IDs in the templates.

## 6. Design for adoption safety

Existing resources are being brought under declarative management. That is more sensitive than creating a new empty environment because an incomplete PUT can change a live resource.

The following controls were therefore built in:

- `audit-existing.bicep` references resources without modifying them;
- project-connection management defaults to `false`;
- the App Insights API-key connection is not recreated without its missing credential;
- capability hosts are excluded until captured;
- the GitHub action only compiles on normal PR/push events;
- Azure what-if/deploy is manual and restricted to `main`;
- `what-if` is the default operation and its output is retained as an artefact;
- deployment mode is incremental.

## 7. Preserve uncertainty instead of filling gaps

The snapshot did not include complete role assignments or capability-host definitions. These are material to a greenfield Agent Service recreation. The kit records them as explicit follow-up items and includes a repeatable capture script.

No role assignment, capability-host name or secret was inferred merely because it would make the template look more complete.

## 8. Produce the manual equivalent

The accompanying manual guide explains how the same result could be produced without this automated analysis:

1. inventory the resource group;
2. capture each resource as JSON;
3. distinguish writable from read-only fields;
4. look up the Bicep schema for each resource;
5. author one resource/module at a time;
6. compile and lint;
7. run an existence audit;
8. run what-if;
9. adopt resources incrementally;
10. separately manage control/data-plane objects.

That process is intentionally included so the IaC is understandable and maintainable rather than a black-box generated artefact.
